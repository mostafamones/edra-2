# Attendance integration

Current implementation reference. [Product teaching/attendance](../../../docs/product/domains/teaching.md) owns intended rules; [OpenAPI](../../../docs/api/sessions-attendance.openapi.yaml) owns HTTP shapes. Source names publish/publication remain wire identifiers for the product action Finalize.

Attendance for a started session: draft inputs, positive check-ins, explicit publication with corrections, realtime collaboration, and the token API used by the future phone app. Schema: `supabase/migrations/20261005170000_attendance.sql`. Sessions (start, end, roster snapshot) belong to the sessions module.

## Current source behavior

- Every roster student starts **Unknown** (version 0, no row). Inputs: Present, Late, Absent, Excused, or back to Unknown. Late is set by staff, or automatically by a check-in accepted after the caller's `lateAfterMinutes` deadline (measured from the session start; 0 or omitted disables it; exactly at the deadline is Present).
- Nothing marks students absent or publishes automatically, including ending a session. **Mark unrecorded absent** (`markUnrecordedAbsent`, `public.mark_unrecorded_absent`, HTTP `POST .../attendance/unrecorded-absences`) is an explicit, revision-reviewed command for a mandatory session: every `expected` roster entry still Unknown becomes Absent in one transaction at any roster size, with one sheet revision bump and one receipt (`unrecorded_absent`). Eligible/unexpected students and recorded values are untouched. A stale reviewed revision changes nothing (`outcome: stale`; HTTP `409 ATTENDANCE_REVIEW_STALE` with `details.revision`); zero targets is `unchanged`.
- **Check-in** (by record UUID, or by an academy-local student code resolved by the database in the same transaction via `check_in_attendance_by_code`; the HTTP/server-action contract accepts exactly one of `student_id`/`studentCode` or `annual_student_record_id`) is a positive input: Unknown → draft Present (`recorded`), or draft Late when `lateAfterMinutes` is above 0 and the check-in is accepted later than that after the session start. The shared engine `edra_private.apply_check_in(…, p_late_after)` takes its locks, captures one server instant (`clock_timestamp()`), and writes the final status, `checked_in_at`, version, sheet revision and receipt in one transaction for both identifiers. UUID check-ins go through `public.check_in_attendance_with_late` (the four-argument `check_in_attendance` stays for older callers and never marks Late). Present or Late → `already_recorded`; nothing changes, including the first check-in time. Absent or Excused → `review_required`; nothing changes. Only roster students can be checked in: others get `not_on_roster` (same academy and year) or `student_not_found`. Code failures: `student_codes_disabled`, `student_code_not_found`, `student_code_retired`, `student_code_ambiguous` (API codes `STUDENT_CODES_DISABLED`, `STUDENT_CODE_NOT_FOUND` 404, `STUDENT_CODE_RETIRED`, `STUDENT_CODE_AMBIGUOUS`). A retry replays the original acknowledgment (stored with the resolved record and assignment for code requests), not the latest state. Fingerprints bind the tagged identifier and the Late-after option (omitted equals 0) for both identifiers; `check_in_attendance_with_late` also replays a receipt stored by the four-argument command under the same key, session and record unchanged (its threshold was never recorded, so Late is never applied retroactively). The unused web scan field (`components/scan.tsx`) submits the exact code and shows only server acknowledgments; the live web entrypoint is the manual picker (`components/check-in.tsx`).
- Check-ins work only while the session is live. After it ends, staff can still edit, bulk-change, and publish while the academic year is open. A closed year makes attendance read-only. So does an archived session: every mutation (UUID or code check-in, manual/bulk edit, finalization) returns `session_archived` (API `SESSION_ARCHIVED`, 409) under the session lock, while stored receipts still replay; `permittedActions` are all false and the sheet's `session.archivedAt` is set. A restored session is editable again (it stays ended).
- Manual and bulk edits carry the `expectedVersion` the user saw. A stale version applies nothing and returns the current rows (`conflict`). Explicit bulk changes are all or nothing (max 500, `MAX_SELECTED_CHANGES`); larger selections are rejected, never truncated.
- **Unexpected attendees** (`searchAttendees`/`addAttendee`; `public.search_attendee_candidates`, `public.add_session_attendee`; HTTP `GET`/`POST .../attendance/attendees`): staff explicitly append an active annual record of the session's academy and year (online-only and out-of-audience students included) to a live or ended, unarchived session in an open year. The new roster snapshot has `origin = 'unexpected'`, the record's own placement, and `added_by`/`added_by_name`; original snapshots and the student's placement never change and authenticated callers still cannot insert roster rows directly. The append bumps the revision against a reviewed `expected_revision` (`stale` otherwise), stores an `add_attendee` receipt, and is a stored no-op (`already_on_roster`) for a student already on the roster. Archived records are `student_archived`. Adding never checks in; unexpected entries never enter "mark unrecorded absent" or produce an expected-absence effect.
- Every draft change bumps the session's monotonic attendance **revision** (separate from the session's `metadataVersion`). Publishing names the revision that was reviewed; a newer save makes it `publication_stale`.
- A changed taught-unit save also bumps that revision before first finalization, so an older attendance review cannot silently finalize a different content list. The finalization dialog summarizes taught units. First finalization freezes the content list, including an empty one; ordinary attendance corrections do not change it in this slice. See the content module's `teaching/README.md`.
- Publication snapshots what became official (`attendance_publications` + immutable items). Later edits are **pending corrections**; published values stay official until republished.
- Attendance history is never deleted. Sheets, records, publications, items and effects reject deletes (publications and items also reject updates), whether or not attendance was finalized; no session setting lifts these guards. Draft edits update rows in place.
- Every write takes an idempotency key (UUID per action, reused on retry). Clients keep the whole command (body and key) after an uncertain outcome (network failure, 429, 5xx, unreadable acknowledgment) and retry it unchanged; the web manual check-in keeps the student, Late-after and key until acknowledged or dismissed. The response is stored with the write, per user; a retry replays it; a key reused for a different request is `idempotency_conflict`. Conflicts and `review_required` are not stored. Records are kept (no expiry job yet).
- Locking: the sessions row first (`for no key update`, which serializes with `end_session`), then the academic year (`for share`).

## Publication effects (outbox only)

`attendance_effects` records official effects once per student and session: Present/Late → `explanation_access`; Absent on a mandatory class for an expected student → `absence_event`; Excused and Unknown → none. A correction that no longer supports an earlier effect records `revocation_review` (owner policy pending). **Nothing consumes the outbox yet**: no access is granted and no parent is notified until those modules exist.

Archival contracts (migration 20261013200000_session_archival.sql), for every current and future consumer:

- **Counted attendance** is `public.counted_attendance`: finalized values of non-archived sessions only. Any total, rate, absence summary or recovery projection must read it (or apply the same session predicate). Stored values are never rewritten; restoring a session makes the same official values count again, without a new publication or effect. No reporting consumer exists yet.
- **Pending effects**: archiving records each still-unprocessed effect of the session in `attendance_effect_suppressions` (effects themselves stay immutable). A stopped effect is never delivered, even after restoration; already processed effects (issued access, sent messages) are untouched. A future consumer must claim through `edra_private.claim_attendance_effect(effect_id)`, which takes the session row `for share` (serializing with archival) and returns the effect only while it is unprocessed, unstopped and its session unarchived; it marks `processed_at` in the same transaction it dispatches in. Nothing in the app calls it yet.

## Realtime

Private Broadcast channel `attendance:<academyId>:<sessionId>`. A trigger on `attendance_sheets` sends `attendance_changed` with `{ session_id, revision, published_revision, publication_count }` after commit; clients refetch. `can_join_attendance_channel` checks topic shape, membership, and that the session belongs to the academy. Members may send presence only (no broadcasts). The web screen rejoins every 20 minutes, refetches on join, focus, and every 60 s, and polls every 15 s while realtime is down.

## Public API

Client-safe (`index.ts`): `recordCheckIn`, `saveAttendanceChanges`, `markRemainingAbsent`, `findAttendees`, `addSessionAttendee`, `publishReviewedAttendance` server actions; `fetchAttendance` and query keys; types.

Server (`server.ts`): `getAttendance`, `checkIn`, `changeAttendance`, `markUnrecordedAbsent`, `searchAttendees`, `addAttendee`, `publishAttendance` (each takes an optional `Authority`; default is the cookie session), and the `/api/v1` response builders.

Deployment order: apply migrations `20261019100000_attendance_unexpected_origin` and `20261019100100_attendance_corrections` before shipping clients that call the new RPCs/routes. Older UUID and code clients keep working; rolling back clients leaves the additive functions, receipts and roster rows in place.

HTTP: `GET /api/sessions/<id>/attendance?academy=` (web, cookie) and the bearer-token `/api/v1` endpoints documented in `docs/api/sessions-attendance.openapi.yaml`.

Web: the `AttendanceSection` component, shown under session facts at /<academySlug>/attendance/<id> on the staff host (internal /app/[academySlug]/attendance/[id]). The old `/app/attendance/<id>/attendance` route redirects there.
