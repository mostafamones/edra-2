# Exams integration

Current staff implementation of EDRA-78. Intended behavior is in [product assessments](../../../docs/product/domains/assessments.md) (**Quizzes and exams**, **Marking and announcement**, **Corrections and history**, **Exam staff delivery boundary — EDRA-78**); [OpenAPI](../../../docs/api/exams.openapi.yaml) describes the bearer reads and the not-yet-operational student contract (EDRA-83 handoff).

Exams are their own domain. They follow the final quiz rules (including the 20261014 quiz refinements) but share no rows, functions or history with quizzes, and nothing here imports quiz internals.

## Schema and migrations

- `20261014120811_exams.sql`: exams, audience groups, parts (Question Sheet / Written Work), questions, choices with one correct choice, readiness issues (including `timer`), derived phase, preparation and availability commands, exam quota buckets.
- `20261014120814_exam_work.sql`: per-student work aggregate, the single online attempt, saved answers, question-aware departures, physical drafts, the single accepted submission, private marks, immutable corrections and official result revisions, deduplicated result/solution effects, closure settlement, staff reads, the student domain and the year-close guard (`academic_years_settle_exams`).
- `20261014120817_exam_deadline_worker.sql`: Supabase Cron job `edra-exam-deadlines` (every 30 seconds) running `edra_private.run_exam_deadlines`.

Students never read exam tables (RLS allows active academy staff only; departures, answers, marks, effects and request replays have no client grant). The student projection is `edra_private.exam_student_state`, built field by field; the student overview is `edra_private.my_exam_overview_json` (EDRA-232). Every write is a security definer command that rechecks live role, suspension, academy, open year, archive, locks, window and versions. Effects in `exam_result_effects` have no consumer yet: recording one is not parent delivery, content release or video playback.

## Rules in force

- Preparation may be incomplete (no audience, timer or parts). Readiness is derived and requires the individual timer: there is no untimed online exam. Availability is a separate Owner/Head Admin/Admin setting. Actual closure is the scheduled close plus two minutes; nothing reopens afterwards, and once work exists the close only moves later.
- Eligibility is live (current placement); the student list adds every historical participant. New physical answers, physical confirmation, online starts, answer saves and explicit submission require current eligibility; leaving the audience keeps drafts and received work, and timer/window/departure settlement of saved work still happens. Target and timer lock when work begins; the structure locks on the first saved answer, departure, physical answer or mark, and at any accepted submission. Model answers, title, instructions and solution notes stay editable.
- Physical drafts and confirmation work once the exam is ready, before opening or without any window, and stop at actual closure.
- Online and physical drafts coexist. The first online final submission or physical confirmation is the single accepted submission; the other draft stays as history.
- Deadlines: `deadline_at = started_at + timer`, never reset. Timer when the deadline is at or before actual closure (a tie included), otherwise `window_closed`. `submitted_at` is the effective time, `processed_at` the settlement time. Never-started students get nothing.
- Departures (`record_exam_departure_for(exam, record, event_id, question_id)`): stored once per event with the question, its original number, ordinal and outcome. First and second warn and return the next non-excluded question (null after the last); the third submits the saved answers as `kicked`. A repeated event returns its original departure (`duplicate`); the same event id for another question is `idempotency_conflict`. A due deadline is settled first and wins. Kicked is graded normally.
- Scoring, announcement, corrections, exclusions and solution qualification match quizzes: automatic online work (including timer, kicked and window_closed) is announced in its acceptance transaction; everything else by staff, all-or-nothing per batch, against the expected scoring revision. Online solutions qualify at actual closure; physical at closure plus an announced result, in either order.

## Concurrency and deadlines

Lock order for every entry point: academic year (share), exam row (`for update` for exam-wide commands: preparation, window, archive, corrections, closure settlement; `for key share` for per-student commands), the student's annual record (share, for the placement check), `exam_work` rows in record order, attempt rows. The year comes first because a direct `academic_years.closed_at` update holds the year row before its trigger settles exams. Database time is read after the locks. Every command and the detail/student reads settle due work first; the paginated list is a read-only snapshot reporting `processing_pending` and `closure_settled_at`. Late saves, confirmations and departures return `finalized` / `source_conflict` outcomes rather than errors so the settlement commits.

Year closure settles due exam work in the same transaction and is refused with `exam_work_pending` while an attempt is still running. Archive is refused for the same reason and never resets work.

Worker monitoring: `edra_private.exam_deadline_runs` (counts, failures, largest cutoff-to-processing lag), `edra_private.exam_deadline_health()` and `cron.job_run_details` for `edra-exam-deadlines`.

## Integration dependencies (not implemented here)

- **Student accounts:** `edra_private.exam_caller_record` resolves the caller through `edra_private.student_caller_record` (EDRA-80): the account's connected, non-archived, not independently suspended annual record in the exam's academy and open year, from an ordinary (not recovery/revoked) session. Unconnected or suspended callers fail with `student_link_unavailable`. Never replace it with a caller-supplied record id or phone match.

Since EDRA-232, `edra_private.exam_content_access` denies attached exams on every student entry path (`content_unavailable`) and discovery excludes them; standalone exams need no release. - **EDRA-83 release dependencies:** EDRA-233 supplies the gated answering surface below; EDRA-234 supplies fullscreen capability/acquisition and departure detection; EDRA-235 adds the read-only post-qualification review and text/image solutions described below. Student teardown has a bounded cookie-only departure POST; no student bearer API exists.
- **Media (deferred by the owner):** written answers are text and physical written work is marked by hand. Document/photo evidence, answer-document assets, file storage and solution videos are not implemented; solution release covers the key, model answers and solution notes.
- **Effects consumers:** parent notifications, reports and playback grants read `exam_result_effects` in their own modules.

## Student answering and recovery — EDRA-233

Migration `20261020004701_student_exam_answering.sql` adds private-to-clients `exam_editor_claims` rows: one hashed random token per attempt, increasing generation and a database-measured 45-second lease; heartbeats run every 10 seconds in a separate quota bucket. Caller identity still comes from the connected ordinary-session annual record. Claim expiry never resets the attempt or its deadline. A different live editor receives `busy`; there is no takeover. The entry component holds an exclusive Web Lock before reusing a sessionStorage token. Without Web Locks it waits for lease expiry instead of reusing a copied token.

The cookie actions are `enterStudentExam`, `claimStudentExamEditor`, `renewStudentExamEditor`, `releaseStudentExamEditor`, `readStudentExamAnswering`, `saveStudentExamAnswers`, `submitStudentExam`, `recordStudentExamDeparture` and `signStudentExamImages`. Their database counterparts are listed in `docs/api/exams.openapi.yaml`. `enterStudentExam` atomically starts/resumes and claims, returning attempt metadata and the claim, never question material. The fenced read returns allowlisted questions, choices, own answers, original numbering, exclusions, account/attempt identity and server time. Terminal responses return status only. At EDRA-233, production `examEntryIntegration` was **null** pending EDRA-234; EDRA-234 registered it (below).

`StudentExamAnswering` is exported from the browser module entry point. It renders choices and text answers with the existing shadcn primitives, one question at a time, navigation, server-relative timer, acknowledged save feedback, field conflicts and the unanswered-count confirmation. The serialized answer queue coalesces typing for 500 ms, flushes on navigation and submission, and persists immutable commands plus newer drafts and their acknowledged baselines in IndexedDB. Unknown outcomes retry the original key/version/body/generation. A reclaimed generation can resolve an accepted old receipt but cannot execute an old unaccepted command; the client reconciles before creating fresh work. Late receipts never replace newer acknowledged answers. Patches are bounded at 300 questions. Confirmed submission freezes edits, acknowledges saves, then retries its durable submission key. Server finalization removes questions immediately and returns to the overview once.

Journals contain pending answers/command metadata only, keyed by verified account and globally unique attempt identity (the attempt binds its academy/exam); no question bank, authentication credential or signed URL is persisted. Acknowledged entries are removed. `exams/browser.ts` exposes the narrow auth cleanup hooks: AuthProvider purges other accounts at identity changes and captures native POST sign-out forms to clear journals before navigation, including when no answering component is mounted. Storage failures keep memory edits and expose the loss of refresh recovery. The initial read purges stale account journals before loading pending work.

Question-image authorization checks the ordinary caller, active attempt, live claim and references in current non-excluded prompts/choices. Only authorized `assignment-images/<academy>/<image>` paths are signed with a server-only credential, for 60 seconds. The read-only shared URL resolver preserves staff upload behavior. Each mounted attempt has a separate memory query cache; renewal stops after ownership loss/finalization. Already-issued URLs retain bounded residual validity. EDRA-234 uses the stable document root so body-portaled dialogs remain descendants; actual hosted dialog verification remains required.

### EDRA-234 lifecycle handoff

`ExamAnsweringProps` now requires the acknowledged `StudentExamAttemptState` and `StudentExamEditor`. Entry owns the browser lock until the surface unmounts. `onLifecycle` receives `attemptId`, `currentQuestionId`, `recordDeparture`, `setEditBlock`, `getState` and `subscribe`, and receives null on teardown. `recordDeparture(eventId)` durably records the logical event and original generation before delivery, independently of save retries; EDRA-234 must correlate browser signals into one stable event id. It applies the returned next question, including null after the last question, and reports authoritative warning/kick/finalization. Before acquiring a replacement claim, entry delivers any journaled departure with the previous token and original generation. A pending latest-generation event is accepted after lease expiry while that generation has not been replaced; replaced generations cannot create departures or gain writer powers. Event id replay uses the engine's original receipt, and never acquires a lease. The authenticated ordinary session and original cutoff remain mandatory. Expiry of a lease alone never manufactures a departure.

`setEditBlock` pauses editing behind EDRA-234's fullscreen return control while the original clock continues. `getState` exposes departure count, pending delivery, block and finalization; it does not expose marking. EDRA-234 supplies fullscreen capability/acquisition/exit and departure detection before registering the integration. No permissive fullscreen stub or production harness is shipped. EDRA-235 owns qualified answer review and solutions; EDRA-236 owns the integrated release checks.

## Fullscreen and departure integration — EDRA-234

`student/integration.ts` registers the standard element-fullscreen adapter and `FullscreenExamAnswering`, which composes the existing answering surface, Alert and Button. Start/Resume calls `requestFullscreen()` on `document.documentElement` synchronously from the click, verifies the resulting element, then recovers pending departures and enters/claims. Capability uses actual request/exit APIs, connected document and `fullscreenEnabled`; there are no device-name guesses or prefixed/video-only fallbacks. A refused acquisition starts nothing. Entry remembers lost visibility/fullscreen during its request and accounts for it only after an acknowledged active claim. Unknown entry outcomes recover the original database attempt; they never reset time.

`ExamDepartureMonitor` attaches synchronously on acknowledgment, before material loads. Visibility-hidden, fullscreen exit and pagehide share one latched event/context/generation. Link navigation and browser history departures reuse that episode; unmount, focus, networking and lease expiry are not signals. BFCache pageshow uses answering's resync, retaining the episode and requiring an explicit fullscreen return. Rearming needs authoritative acknowledgment, visible document, the expected fullscreen root and explicit Continue/Return. Pending delivery blocks answers, navigation, conflicts and submission while the original timer runs. Blocking remounts the question subtree to close its image portals; the confirmation dialog is suspended. Other authority/finalization blocks remain separate.

The lifecycle is available during loading and adds `departureContext()` and `currentToken()` (the token stays transient). `recordDeparture(eventId, context?)` freezes provenance independently of save delivery; pending events prevent replacement claims. With no selected question, the last displayed question is retained; it never wraps after the final question. A departure before any material is displayed has null question context. Migration `20261020123036_student_exam_departure_context.sql` permits only both-null or both-present question id/number, preserves foreign-exam checks, immutable rows, null-safe retry comparison, lock order and deadline precedence. A context-free warning continues at the first non-excluded question after material loads. Staff history also represents that null context explicitly.

At the first signal, account/attempt-scoped localStorage holds only event/question/generation metadata (event id is episode identity). The IndexedDB v3 journal accepts v2 without losing drafts or submission intents. Pagehide immediately attempts a bounded keepalive POST to `/api/student/exams/<examId>/departure`, using the same event and transient claim token; enqueue is never acknowledgment. The route requires the configured student Origin, rejects cross-site/mixed bearer requests, strictly validates at most 2048 body bytes and composes the existing ordinary-cookie fenced service. Its private/no-store response contains receipt metadata only. No service-role path, credentials in URLs, token logs, answers or result material are involved.

Recovery combines breadcrumb and journal by event id before replacing a generation. Authoritative warnings are carried into the resumed UI and require Continue. Missing sessionStorage credentials or a refused generation reports an undeliverable event once, removes only its departure metadata and preserves answer/submission recovery for legitimate resumption. It never delivers under a replacement generation. Sign-out/account changes purge fallback metadata through the existing hooks. Lifecycle delivery remains best effort: unreported crashes, storage denial and closed-tab token loss cannot guarantee a penalty. Signals are client evidence, not cheating/proctoring proof.
