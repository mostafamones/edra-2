# Staff content workspace

`/<academy>/content` is the searchable content library and program picker. Programs inherit the academy's existing academic year, level and optional track; a unit never asks staff to configure them again. `/<academy>/content/<unit>` edits a unit. `/<academy>/releases` opens the same workspace filtered to published lessons; the In review filter surfaces submitted drafts.

After a unit loads, its editor prefetches history, compatible assessments and reusable published materials in one background request, with parallel server reads. The panels share a one-minute query cache and existing content invalidation refreshes it after changes. Reuse reads only the latest publication document for each published source; selecting a source needs no additional unit-detail request. Each panel reports and retries its own loading failures.

## Library sheet

Edit, History and Content in a library card's menus open `UnitSheet` over the library; the card itself still opens the full editor. Edit shares `UnitSettings` with the editor's Settings panel and autosaves the same draft under the same permissions; closing saves anything pending and only drops a draft that can't be saved after confirmation. History's newest draft entry and the card menus offer one next step (`unitAction`): Save version until the unit is first published, keeping the working draft as its own entry through `save_content_draft_version` without changing the unit's version; after that, Publish changes for managers or Send for review for the author. First publication stays in the editor. Content lists the working draft's material with previews and no editing.

## Labels

Units use their own `content` [label catalog](../labels/README.md), separate from assessment labels. `set_content_unit_label` lets any active staff member apply or remove labels, including on archived units and in closed years, without changing the unit's version, draft or publications. Copies do not inherit labels. Library cards look up their labels in the catalog, so renames and recolors show without refreshing the workspace; selecting labels narrows the library from its view options.

Transactional RPCs enforce ownership, manager powers, open years, optimistic versions, attachment compatibility and source provenance. The database—not disabled controls—decides permission.

## Material and copying

The editor supports ordered explanation videos, documents, existing or newly created assignments/quizzes/exams, and answer videos or documents attached to assessments. One upload area accepts either a video (explanation) or a document. Answers are listed under their assessment. Every row drags: dropping a file or row onto an assessment (or one of its answers) makes it that assessment's answer in the draft; dropping on a row's top/bottom half reorders, and the closing upload row moves a dragged row to the end; an answer dropped among top-level rows is unlinked back to an explanation/document. Removing an assessment keeps its answers as ordinary material. Documents can also be attached to an explanation video as its supporting material: an attached document is a `document` item with `attached: true` stored right after its video, so whole-unit copies keep the link while single-material reuse drops it (migration `20261025180000_content_attached_documents.sql`; students still see these items in order without nesting). Selecting a row (click or Tab) opens a bottom bar with Move up/down, Add answer or Attach document, Detach and Remove; arrow keys move the selection and Escape clears it. Migration `20261025170000_content_answer_documents.sql` lets answer items reference document assets (explanations still require videos, documents still require documents) and signs answer documents for qualified students like answer videos. Drafts save automatically about a second after the last change; text fields save once they lose focus (Enter on titles), so a burst of moves is one save. The header shows Saving/Saved/Unsaved, or Not saved · Retry after a failure, and Undo steps back through the saves made in this session (or drops pending edits). A version change from elsewhere replaces the local draft and clears Undo. History lists only known staff; an entry without one shows Untracked. New assessments are created and attached atomically using the unit's program/year, then completed in the existing assessment editor. These are fresh incomplete assessment preparations, not ready/published assessments.

The existing-assessment picker is unit-scoped. Its paginated database command reuses the save/publication compatibility checker, including complete group audience coverage, academy/year, grade/optional track, archival and the one-unit attachment rule. Already attached assessments and unsaved selections are excluded. Creating directly inside the unit remains available when no compatible standalone assessment exists. The final save still revalidates because eligibility can change concurrently.

## Media

Videos upload from the browser directly to Mux through a server-authorized upload URL, with signed-only playback policy. Files never pass through a Next.js server action. The provider adapter is `src/lib/video/mux.ts`. Staff previews require current membership and short-lived RS256 playback tokens. The official Mux player renders playback; this is access control, not DRM.

`content_assets` tracks uploading/processing/ready/failed state. The editor polls pending uploads and verifies their current provider state server-side. An optional `/api/webhooks/mux` handler authenticates the raw body using `MUX_WEBHOOK_SECRET`, checks timestamp tolerance and synchronizes via provider IDs. A webhook endpoint has not been registered automatically because a reachable development deployment URL was not supplied. Polling does not depend on a webhook.

Upload registration is durable separately from the unit document. The editor's Uploaded files section lists this unit's registered files that are not attached to the current draft, including uploads completed before leaving without saving. Staff can preview/check and attach an existing upload as an explanation, document or assessment answer without creating another provider upload. Recovery only reads existing unit-scoped, RLS-protected asset metadata; it never auto-publishes, overwrites unsaved edits or deletes provider assets. Leaving during an active upload also triggers the browser's unsaved-work warning.

Unused videos also have a confirmed **Delete permanently** action. Save any draft removal first. The server checks live editing authority and rejects deletion if any saved unit or publication revision references the asset, including archived history and copies. A database reservation and shared reference locks block racing attachment/publication. The server cancels waiting Mux uploads or deletes their resulting assets before removing the Edra asset row. Failures preserve a retryable reservation, and provider 404/204 responses make retries safe. Pending deletion blocks preview, reattachment and provider-state synchronization. This permanently removes unused video content; Mux may retain cancelled-upload metadata, which has no video storage. Document deletion and purging published academic history are outside this action.

Credentials stay in ignored local/deployment secrets, without `NEXT_PUBLIC_` prefixes. Privileged state writes happen only after staff authorization or verified provider callbacks.

## Student learning and access

Progress and resume are owned by `progress/`. Explanation videos complete at 90% unique watched timeline coverage; documents and answer materials are excluded. Attached assessments use official assignment received-work states (`submitted`/`late`) and quiz/exam submission records, never draft attempts or marks. Unit and browse summaries recalculate against the current publication while preserving prior activity for replaced/removed videos.

The player checkpoints every five seconds and saves on pause/close. Overlapping watched sections are merged; seeking and buffering do not contribute. The newest opened session controls resume, and ordered checkpoints prevent older writes from replacing its position. Activity belongs to an annual student record, unit and immutable asset, so copied/reused units and new-year records start separately. Every start/save rechecks live playback authority. Progress grants no access and satisfies no prerequisite. Abrupt browser/network loss may leave recent unacknowledged seconds unsaved.

Mux supplies the trusted video duration on processing or first authorized progress start for older assets. Private progress tables are RPC-only with RLS enabled. The `content_progress` disposable database suite covers coverage, ordering, isolation, publication edits and access denials; never run its fixtures on shared development.

`LearningBrowse` and `StudentLearningUnit` are the client public components; `readLearningList` and `readLearningUnit` are server exports. Connected students enter `/<academy>` on the student host to see published units for their current annual grade/optional track, newest publication first. `/<academy>/units/<id>` shows ordered metadata, access status/expiry, unit-code redemption and the annual extension. Client caches are scoped by account and academy; account changes hide stale learning data. Answers remain locked and attached assessments unavailable until their separate eligibility/execution integration is supplied.

`access/` owns schemas, server actions, bounded data reads and composed staff controls. `UnitAccessPanel` appears on previously published unit editors: staff can search matching records, grant default access, add time, inspect history, generate/copy/export codes; managers revoke grants or unused codes. Draft, archived and closed-year issuance is denied. Confirmation binds the displayed current grant and published revision; stale changes require a fresh review.

The database ledger is append-only, with a single effective grant head per annual record/unit. Expired/revoked heads never fall back to earlier grants. Full grants start at issuance; explicit extensions retain active remaining time or start now after expiry. Revoked access is not restored by an extension. One annual 48-hour student extension is shared across the academy's units, only after a prior grant expires. Mutations use actor/payload-bound request IDs and durable receipts so retries cannot duplicate grants, code sets or time.

Codes are 128-bit random single-use identities. Generation accepts 1–1,000 codes with no duration override. Redemption resolves connected annual participation, checks eligibility and uses the current published default at redemption. Only one code redemption is permitted per annual record/unit. Raw codes are staff-only; all new public tables deny direct authenticated/anonymous reads and writes. Authorization lives in bounded RPCs, with private helpers revoked from client roles.

`openLearningMaterial` first invokes the student-only material authorization RPC. Explanation videos and supporting documents require the same active unit access and a material reference in the current published snapshot. Video/thumbnail/storyboard JWTs last at most 15 minutes and never beyond grant expiry; private document URLs last at most two minutes and never beyond grant expiry. Credentials already issued remain valid until their bounded expiry; subsequent issuance rechecks live authority. The student player renews credentials and stops at grant expiry. This does not supply DRM or answer-video access.
