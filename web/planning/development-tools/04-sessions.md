## Fixed control-session design

This design preserves real Supabase password sessions and the existing shared cookies.

1. Server configuration: explicit `EDRA_DEV_MODE_ENABLED`, the allowed cloud project reference and real developer UUID allowlist. First version requires Next development execution (`NODE_ENV !== 'production'`); hosted preview activation is separate scope. Unknown/mismatched target disables controls. Secrets stay server-only.
2. Store tooling state under `edra_private`: runs, generated accounts/contacts, developer allowlist mirror, controls and last switch-command receipts. Public RPC adapters required by the web server are executable by `service_role` only, with fixed empty search paths. No direct browser grants to registry or control tables. Read/update control rows only through bounded RPCs, never a browser-provided SQL filter.
3. Account secrets and original session tokens use authenticated AES-256-GCM encryption with a server-only 32-byte key, distinct from the random dataset seed. Bind ciphertext to project/run/user/control identity as appropriate. Never expose original tokens or generated passwords through JSON, logs or localStorage. Missing encryption configuration disables switching; never fall back to plaintext.
4. On entry, validate the real developer's ordinary session and allowlist membership server-side. Read the actual user/session IDs from verified claims. Save the original access/refresh pair encrypted in the private control row, with the current academy destination. Use a random 256-bit opaque browser control token; store only its hash in the control row. Set an HTTP-only, SameSite=Lax cookie on the existing staff/student parent domain, Secure when HTTPS. Absolute control lifetime is two hours. Do not use the active target's role as developer authorization.
5. Every status/switch/return/exit operation checks the opaque token, control expiry, live original `auth.sessions` row and developer allowlist. For a switch, additionally check the current Supabase session matches a session issued by that control, or its original developer session when the control explicitly records the original identity as current (initial/direct entry or Return to staff). The selected test target must be a generated account of the same ready run. Use a same-origin POST and an expected control revision plus command UUID. Reject arbitrary user IDs, academy IDs and redirect URLs. List targets from the registry.
6. Serialize switch commands using a DB-backed lease/CAS on the control revision. A repeated latest command reuses its encrypted issued-session receipt; a stale older command returns conflict instead of switching backward. Store the minted target session before emitting its cookies so an interrupted response can be retried. Keep bounded prior/current session bindings for that pending command. Lease loss must never publish a session; invalidate a newly minted orphan through the Auth Admin API.
7. Mint the target via server-side `signInWithPassword` using its stored generated credential, with persistence/auto-refresh disabled on the transient client. Existing ordinary auth cookies receive the target session through the SSR cookie adapter. Do not use magic-link/OTP sessions or fabricate JWTs. Normal application DB clients continue to use the target session with RLS.
8. Narrowly extend the existing session-authority check for registered generated accounts only: their `session_id` must belong to a live control whose original developer session/allowlist and run remain valid. Preserve every existing revocation/recovery check and all ordinary-user behavior. This prevents a surviving copied test JWT from retaining domain authority after its developer control expires or is revoked. A test account without valid control is not an alternate developer login.
9. When entering student view, store a tagged prior staff target (original developer or generated staff account) and validated students-directory URL (allowlisted query fields, no arbitrary external next link). Direct View as student from the real developer's normal synthetic-academy directory creates the control and tags the original developer as prior staff. Return signs into the same generated staff target, or refreshes/restores the original developer session while retaining the valid control if that was the prior staff identity. Exit refreshes/restores the encrypted original developer session through the SSR adapter, invalidates the control and revokes its issued test sessions with the supported Auth Admin API. If the original session is revoked/unrefreshable, terminate preview and require normal login; never restore stale tokens as authenticated authority.
10. Real sign-out invalidates the control and revokes issued test sessions and the original session as appropriate, then follows existing sign-out cleanup. Role switching does not use global sign-out, which would revoke the preserved original session. Retry/cleanup failures are surfaced as functional errors; inactive-control RLS denial remains effective even if provider session cleanup must be retried.
11. Use full navigations after successful switches to rebuild the shell and clear caches/channels/exam-journal account state. Add a non-sensitive BroadcastChannel/storage-event signal across same-origin tabs and retain the existing cross-origin focus/navigation revalidation. Already-rendered hidden tabs may show old pixels until revalidation, but server actions execute as the actual shared session. Disable identity-bound mutations while the browser knows a switch is pending. Do not promise independent tab identities.

## Endpoint/state contract

Use GET `/api/development/status`; POST `/api/development/enter`, `/switch`, `/return`, `/exit`. GET only reports safe display state; it never signs in, changes target or refreshes into another identity. No developer credentials in responses.

POST enter accepts a ready run plus an optional generated-student logical ID and validated staff directory context for direct student entry; absent that target it enters the generated Owner. Other POST bodies contain run/logical target IDs and, for active controls, expected revision and command UUID. The server resolves Auth identities from the registry. Every response is private/no-store. Use existing canonical staff/student destinations, safeRelativePath/return validation and exact Origin checks; no tokens in redirect URLs.

Control states: original → staff target → student target → prior staff target; exit restores original. Switching staff roles updates the remembered staff target; entering another student preserves it. The remembered staff identity can also be the original real developer when entering student view directly from their normal academy directory. Reject nested control creation and arbitrary real-user targets.

Do not revoke the previous target until the newest command/session receipt is durably stored. Bound pending replay to the latest command revision; old requests must not roll the browser backward. Invalid/expired/revoked control denies generated-account domain authority and shows normal login when original restoration cannot succeed.

## Acceptance

A1: Real developer allowlist, target registry and live original session are checked server-side. Ordinary academy owner/instructor/student, revoked/recovery sessions and production mode are denied.
A2: Real password sessions execute ordinary target-role RLS; service-role credentials never authorize normal page data/actions.
A3: Source developer revocation/expiry, control expiry or reset makes generated sessions fail the DB authority check. Ordinary users retain existing behavior.
A4: Same-origin mutation enforcement, target/run mismatch, invalid return URL and tampered cookie/ciphertext are rejected.
A5: Concurrent/stale commands do not cross identities; retry after lost response restores the same latest target session without duplicate side effects.
A6: Return restores staff target; exit restores original; real sign-out revokes control. Account-specific query/journal state is cleared and sessions stay consistent across staff/student origins.
A7: Missing server secret/project config disables the feature without weakening auth. No original refresh token/generated password appears in browser-readable state or logs.
